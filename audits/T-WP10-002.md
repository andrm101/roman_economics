## 4. Issues

1. **Design point (moderate): flat `monte_carlo` cannot apply the other-side rule.** With a flat list, only the "returns to itself" rule runs. Suppose a caller concatenates the two sides of a join and passes them to `monte_carlo` instead of `monte_carlo_join`. Then a cross-side dependency (A on the left dated from B on the right) is kept silently. I checked this: `[A dep B, B]` keeps both. This is narrower than T-WP10-001 issue 1, but it is the same failure mode. The producer flagged it as an [assumption] and argued that it did not meet the escalation condition. I accept that argument: the spec defines the sides whenever a join exists. The researcher should still confirm the reading, or decide whether join analyses must use `monte_carlo_join`. For example, the docstring could say so, or `monte_carlo` could require `left`/`right`.
2. **Design point (minor): self-joins are not supported by `monte_carlo_join`.** If the same records appear on both sides, the call raises a duplicate-ID error. The producer flagged this. The spec does not define the case.
3. **Minor: all records excluded.** If every record is circular or excluded, `statistic` receives `{}` on every draw and there is no warning. My check returned `values == (0, 0)` for `len`. A downstream analysis could report a "robust" result computed on no data. Consider requiring at least one kept record, or warning.
4. **Minor: `seed` is not validated.** `seed=True` is accepted, the same bool/int subclass issue that `n_draws` had. This is outside the contract.
5. **Minor: `lag_join(k=0)` is accepted and always returns no pairs.** The producer flagged this and proposed `k >= 1`. I agree this is for the researcher to decide.
6. **Performance (minor):** `check_unique_ids` now runs inside `draw_dates` on every draw, after having already run in the entry point. This is redundant O(n) work per draw. It does not affect correctness.
